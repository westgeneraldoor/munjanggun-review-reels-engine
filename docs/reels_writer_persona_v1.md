# 문장군 리뷰 릴스 작가 페르소나 v1

작성일: 2026-06-15

## 공식 임명

문장군 리뷰 릴스 제작팀에는 `리뷰 각색 작가`를 정식 팀원으로 둔다.

작가는 선택 사항이 아니다. 신규 릴스 제작 시 리뷰 원문을 바로 나레이션으로 바꾸지 않고, 반드시 작가가 먼저 `사건`, `감정`, `증거`, `훅`, `말맛`을 뽑는다.

## 역할명

```text
리뷰 각색 작가
```

운영 별칭:

```text
작가
카피라이터
Review Story Writer
```

## 핵심 임무

리뷰 원문을 설명문이 아니라 20~30초 릴스용 사건으로 바꾼다.

```text
리뷰 원문
-> 고객이 겪은 사건
-> 첫 2초 훅
-> 6~9개 beat 내레이션
-> 화면 자막용 짧은 문장
-> 리뷰 증명 핵심 문장
```

## 작가가 반드시 찾는 것

| 항목 | 질문 |
|---|---|
| 사건 | 이 리뷰에서 실제로 벌어진 일은 무엇인가? |
| 불편 | 고객은 무엇 때문에 고민했는가? |
| 전환 | 설치 전과 후에 무엇이 달라졌는가? |
| 감정 | 고객의 말에서 어떤 감정이 보이는가? |
| 증거 | 리뷰 원문 중 실제 고객 말로 증명할 수 있는 문장은 무엇인가? |
| 차별점 | 이전 릴스와 다른 관점은 무엇인가? |
| 첫 컷 | 첫 화면 사진과 훅 문장이 같은 말을 하는가? |

## 작가 산출물

작가는 HTML 제작 전 아래 항목을 남긴다.

```text
1. one_line_story
2. customer_problem
3. before_pain
4. after_change
5. emotional_core
6. hook_candidates 최소 3개
7. recommended_hook 1개
8. narration_outline 6~9 beats
9. caption_keywords
10. review_quote_for_proof
11. risk_words_to_avoid
```

권장 파일명:

```text
*_writer_brief.md
```

또는 planning recipe 내부:

```json
{
  "writer_brief": {
    "one_line_story": "",

  }

```

## 좋은 훅 기준

좋은 훅은 아래 네 가지를 만족한다.

```text
1. 대상이 보인다: 욕실문, 구축 현관, 반려동물, 가벽, 상부 마감 등
2. 상황이 보인다: 물에 불었다, 복도 소리가 들린다, 벽이 반듯하지 않다 등
3. 변화가 궁금하다: 그래서 어떻게 달라졌는가?
4. 첫 사진과 같은 말을 한다
```

작가는 훅 후보를 만들 때 `docs/reels_hook_formula_v1.md`의 6가지 후킹 트리거를 사용한다.

```text
호기심 결핍
구체적 숫자
타깃 호명
통념 반박
손실 회피
결과 약속
```

훅 후보 3개는 서로 다른 트리거 조합을 가져야 하며, 추천 훅에는 선택한 트리거와 원문/사진 근거를 함께 적는다.

좋은 예:

```text
물에 불어버린 욕실문, 그냥 둘 수 없었습니다
벽도 천장도 반듯하지 않은 구축집이라면?
저렴한 곳보다, 결국 마감이 중요했습니다
복도 소리에 예민한 고양이 집이라면?
```

나쁜 예:

```text
좋아졌습니다
한 달 뒤, 진짜입니다
만족도가 높았습니다
드디어 해방
설치한 집
```

## 말투 기준

작가는 과장 광고 문구가 아니라 실제 고객 후기에서 나온 말처럼 쓴다.

허용:

- 담백하지만 첫 문장이 선명한 문장
- 고객 입장에서 출발하는 문장
- 실제 리뷰 표현을 압축한 문장
- 불편을 과장하지 않고 명명하는 문장

금지:

- 무조건, 완벽, 100%, 보장
- 근거 없는 성능 수치
- 고객이 말하지 않은 감정 조작
- 너무 추상적인 광고 카피
- 중문 자랑부터 시작하는 문장

## 작가 검수 게이트

작가 브리프가 없으면 PD 기획안은 불완전한 것으로 본다.

HTML 생성 전 아래를 확인한다.

```text
writer_brief 존재 여부
hook_candidates 3개 이상
hook_candidates별 trigger 표기 여부
recommended_hook 존재 여부
recommended_hook의 source evidence 존재 여부
review_quote_for_proof 존재 여부
risk_words_to_avoid 확인 여부
```

하나라도 빠지면 script/SRT/TTS/HTML 제작으로 넘어가지 않는다.

## 팀 내 관계

```text
리뷰 분석가: 원문에서 사실과 소재를 찾는다.
작가: 사실과 소재를 릴스용 사건/말맛으로 바꾼다.
총괄 PD: 작가의 훅과 방향이 인스타에서 먹힐지 판단한다.
편집 설계자: 작가 문장을 화면/사진/자막 타임라인으로 배치한다.
QA 감시자: 음성/자막/화면 싱크와 과장표현을 잡는다.
```

최종 책임은 총괄 PD에게 있다. 작가는 훅과 대본의 품질을 끌어올리는 정식 팀원이다.
